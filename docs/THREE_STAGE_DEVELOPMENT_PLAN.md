# Bixi Seed 三阶段开发路径

日期：2026-08-27

## 一、项目定位

Bixi Seed 是一个面向小团队和个人开发者的轻量应用基座。它预先确定技术栈、目录结构、安全边界和运行方式，让使用者可以在 Windows、macOS 或 Linux 上直接启动一个可用的组织权限核心，并通过 AI 对话逐步创建自己的业务功能。

它不是组织管理软件，也不是单纯的 Skill 或描述文件。组织、成员、角色和权限是所有业务的安全底座；AI 是扩展业务能力的入口；具体业务由声明式功能引擎或受控代码扩展承载。

## 二、固定技术与运行边界

| 领域 | 首版选择 |
| --- | --- |
| 后端 | Python 3.12+、Django 5.2 LTS、Django REST Framework |
| Web 运行 | Uvicorn + Django ASGI |
| 前端 | Vue 3、TypeScript、Vite、Element Plus |
| 数据库 | SQLite，保留后续 PostgreSQL 适配空间 |
| AI | OpenAI Python SDK，默认以 DeepSeek 为示例，优先支持 OpenAI-compatible API |
| 部署 | Windows、macOS、Linux 源码运行、Python 虚拟环境和原生脚本 |
| 数据保存 | 本地 SQLite、配置文件和备份目录 |

首版明确不引入 Docker、微服务、Nacos、Redis、消息队列、分布式事务和 Windows 原生安装包。项目保持源码可读、可编辑，AI 修改代码后可以直接通过脚本重新启动和验证。

## 三、不可破坏的核心原则

1. 核心服务必须能够在没有任何业务功能时正常启动。
2. AI 不能修改核心认证、组织权限、数据隔离和启动代码。
3. 普通业务需求优先转换成声明式 Feature 定义，不直接生成并执行任意 Python 或系统命令。
4. 所有业务数据都必须绑定组织范围，后端不能信任浏览器提交的组织编号。
5. AI 的写入、删除、权限修改和发布操作必须经过工具授权和用户确认。
6. 核心代码、Feature 定义和复杂代码扩展使用不同的生命周期管理。
7. 任何阶段都保留单机运行和脚本启动方式，不为了未来规模提前引入分布式复杂度。

## 第一阶段：稳定核心与最小业务闭环

### 阶段目标

让用户可以在 Windows、macOS 或 Linux 上通过脚本启动一个安全的单体核心，完成组织权限管理、LLM 配置和 AI 对话，并通过 AI 创建第一个不修改核心代码的基础业务功能。

### 开发内容

#### 1. 核心运行基线

- 完善 Windows 的 `setup.bat`、`start.bat`、`stop.bat`、`restart.bat`、`status.bat`、`logs.bat`、`backup.bat` 和 `restore.bat`。
- 同时提供 macOS/Linux 的 `setup.sh`、`start.sh`、`stop.sh`、`restart.sh`、`status.sh`、`logs.sh`、`backup.sh` 和 `restore.sh`，三端保持相同的生命周期语义。
- 启动前自动检查 Python、虚拟环境、配置文件、数据库迁移和端口占用。
- 核心进程使用 PID 文件、日志文件和健康检查管理。
- 支持 Windows 登录、macOS LaunchAgent 和 Linux 用户级 systemd 自动启动。
- 默认只监听 `127.0.0.1`，需要局域网访问时由配置显式开启。
- SQLite 数据库、日志和备份目录与源码分离。

#### 2. 组织权限基础

- 用户名登录、退出、Session 管理和密码安全策略；邮箱不是账号创建前提。
- 顶级组织、子组织创建、组织切换和当前组织上下文。
- 组织使用父子树表达层级，创建子组织必须具备上级组织管理权限；父子组织之间暂不自动继承成员权限。
- 组织成员、角色、权限和角色权限关联。
- 成员资料包含姓名和联系方式；联系方式支持手机号、微信号或其他文本，不强制邮箱。
- 所有者、管理员和普通成员的基础权限模型。
- 权限目录按菜单和操作分组，菜单显示、路由进入和后端接口统一校验权限。
- 后端统一提供组织范围查询和权限判断服务。
- 首批跨组织越权、无成员访问、无权限操作测试。

#### 3. AI 基础能力

- 管理员在系统启动后配置 Provider、Base URL、Model 和 API Key。
- API Key 只保存在服务端，并加密存储。
- 通过统一 Provider 接口访问 OpenAI-compatible 模型。
- 保存组织级会话和消息记录。
- 支持 SSE 流式输出。
- AI 不直接访问数据库，不直接执行 Shell，不直接修改核心文件。

#### 4. 声明式 Feature 最小能力

首阶段只支持常见的轻量业务功能：

- 文本、数字、日期、枚举、布尔等基础字段。
- 列表页、表单页和详情页。
- 基础搜索、排序和分页。
- 创建、查看、修改和删除权限。
- 组织范围的数据隔离。
- 草稿、发布和停用状态。

AI 先生成字段、页面、操作和权限方案，用户确认后写入 Feature 定义。前端提供通用业务对象、客户管理、任务管理和轻量台账等填空式模板，用户只填写关键内容，不必从零组织完整提示词。Vue 通用渲染器再根据定义生成页面，基础服务不需要重新编译或重启。

#### 5. 可复用但不预置业务的基础能力

- 提供统一的文件保存模块，限制文件名、分类目录、扩展名和大小。
- 提供 `.xlsx` / `.xlsm` 的受限 Excel 解析，供后续 AI 生成的业务导入接口复用。
- 提供站点 Logo、登录页欢迎语/描述和首页标题/描述编辑能力。
- 提供统一图标样式和 Element Plus 图标约定。
- 不在基座中提前生成客户、库存、项目、合同等具体业务模块和导入页面。

### 阶段验收

- 新用户在具备 Python 和 Node.js 的 Windows、macOS 或 Linux 机器上可以通过对应 setup 脚本完成初始化。
- 各平台的 start 脚本都可以后台启动核心，restart 脚本可以完成重启，核心异常退出不会留下不可识别的运行状态。
- 用户只能读取和操作自己所属组织的数据。
- API Key 不会以明文出现在接口响应、前端状态或普通日志中。
- 核心在没有任何已发布 Feature 时可以正常启动和登录。
- AI 可以根据自然语言生成一个基础业务功能方案，并在确认后发布。
- 发布 Feature 不修改核心源码、不新增核心迁移、不需要重启核心服务。
- Feature 配置损坏或停用时，核心仍然可以正常启动。
- 能够备份并恢复 SQLite 数据，恢复前检查服务状态，恢复后自动迁移并完成健康检查。
- 管理员可以编辑 Logo、登录页和首页文案；业务页面仍保持为空，由 AI 或开发者按需生成。
- AI 生成的文件导入业务可以复用统一上传和 Excel 解析模块，并受文件大小、格式、组织权限和字段校验约束。
- AI 创建业务功能时可以通过填空式模板生成结构化提示词，同时保留自由对话入口处理临时需求。

### 第一阶段明确不做

- AI 直接生成并执行任意 Python、JavaScript 或系统命令。
- AI 自动删除数据、修改权限或发布不可逆变更。
- 复杂表关联、工作流、报表引擎和代码生成器。
- 微服务、分布式部署、Redis、消息队列和对象存储。
- 多人实时协作和复杂企业 IAM。

## 第二阶段：高效创建真实业务应用

### 阶段目标

让开发者和非技术用户可以通过 AI 与管理界面，在较短时间内创建和维护真实的小型业务系统；同时引入版本、预览、回滚和受控扩展机制，保证业务变化不会破坏核心。

### 开发内容

#### 1. 完整组织权限管理

- 成员邀请、接受、停用、移除和重新加入。
- 成员账号使用用户名，姓名和联系方式作为必备资料维护。
- 角色创建、编辑、复制和权限批量分配。
- 权限按功能、操作和组织范围分组展示。
- 支持业务资源的数据范围策略。
- 组织设置、管理员转移和危险操作二次确认。
- 完整审计日志，记录操作者、组织、对象、操作、结果和时间。

#### 2. Feature 引擎增强

- 关联字段和基础一对多关系。
- 字段校验、默认值、条件显示和计算字段。
- 自定义列表列、筛选器、表单布局和详情布局。
- 批量操作、导入、导出和模板数据。
- 状态流转和有限的业务动作。
- Feature 版本、草稿、预览、发布和回滚。
- Feature 自己的定义数据与核心权限表分离。

#### 3. AI 功能构建流程

将 AI 从“聊天接口”提升为“受控的功能构建助手”：

```text
需求描述
  -> 需求澄清
  -> 功能结构预览
  -> 字段、页面、权限和操作差异
  -> 用户确认
  -> 生成 Feature 草稿
  -> 校验和试运行
  -> 发布或回滚
```

AI 工具必须具备：

- 明确的工具名称和参数结构。
- 当前用户和当前组织权限校验。
- 风险等级和操作确认要求。
- 失败时的事务回滚。
- 每次调用的审计记录。
- 对字段、权限和数据变更的可读差异展示。

#### 4. AI 开发上下文

- 提供机器可读的核心模块、Feature Schema、权限目录和 API 约定。
- 提供标准任务模板，例如新增字段、创建 Feature、增加权限、修复校验和升级依赖。
- AI 完成代码任务后必须运行测试、构建和健康检查。
- 文档中明确哪些目录可以改、哪些目录不能改。
- 让 AI 可以理解当前组织、当前 Feature 和当前版本，但不能读取不属于当前范围的数据。

#### 5. 复杂业务扩展的准备

当声明式 Feature 无法表达复杂业务时，允许创建代码扩展，但必须经过：

```text
草稿目录
  -> 依赖检查
  -> 静态检查
  -> 单元测试
  -> 前端构建
  -> 权限清单审查
  -> 用户确认
  -> 启用
```

第二阶段可以先采用可信代码的独立模块方式，禁止核心启动时自动导入未验证代码。需要更强隔离时，再启用独立本地进程、独立虚拟环境、独立 SQLite 数据库、独立日志和独立端口。

### 阶段验收

- 普通用户可以通过自然语言完成一个包含字段、页面和权限的真实小应用。
- AI 生成的方案可以在发布前预览、修改、确认和撤销。
- Feature 的版本发布、停用和回滚不影响核心登录和组织权限。
- 一个损坏的代码扩展不会阻塞核心启动。
- 管理员可以查到每次 AI 生成和发布的完整记录。
- 开发者可以根据项目提供的上下文，让 AI 完成常见修改，并由测试结果判断是否成功。
- 备份、恢复和升级操作有清晰脚本与失败提示。

## 第三阶段：开放的轻量应用平台

### 阶段目标

让 Bixi Seed 从一个可用的项目种子，演进为有稳定扩展协议、可复用模板和社区贡献能力的轻量应用平台，同时保持单机、源码可改和低部署门槛。

### 开发内容

#### 1. 稳定扩展协议

- 发布 Feature Manifest、权限声明、页面定义、数据定义和操作定义规范。
- 提供 Feature SDK 和示例模板。
- 支持扩展自定义 API、页面和任务，但必须通过核心上下文访问用户、组织和权限。
- 扩展不能自行创建认证体系或绕过组织数据边界。
- 支持声明式 Feature 和代码扩展共存。

#### 2. 独立扩展运行时

对于复杂或 AI 生成的代码扩展，提供可选的本地进程运行方式：

- 核心服务固定运行。
- 每个扩展可以使用自己的虚拟环境、数据库、端口、PID 和日志。
- 核心通过受签名的内部上下文向扩展传递用户和组织信息。
- 扩展可以单独启动、停止、重启、禁用和回滚。
- 扩展故障不会阻塞核心服务启动。

这仍然是单机模块化架构，不引入服务注册中心和分布式治理。进程隔离用于控制扩展故障范围，不代表项目转向微服务。

#### 3. AI Provider 与工具生态

- 增加 Anthropic、Gemini 等非 OpenAI-compatible Provider 适配器。
- 建立统一模型能力、额度、超时和错误提示规范。
- 建立可注册的 AI Tool 协议。
- 支持行业模板、业务工具和可审查的 Runbook。
- 所有工具继续遵守组织权限、风险分级、确认和审计规则。

#### 4. 版本与长期运行能力

- 稳定版本和长期支持版本策略。
- 核心数据库迁移、Feature 迁移和扩展迁移分离。
- 完整备份、恢复、升级和回滚流程。
- 运行日志、健康检查、错误诊断和基础监控。
- 兼容性检查和升级前预检。
- 为 Windows、macOS 和 Linux 脚本保留清晰的安装、启动、关闭和重启体验。

#### 5. 生态与真实方案

- 提供客户管理、项目管理、任务管理、资产管理和内容管理等模板。
- 为每个模板提供示例数据、权限说明、AI 对话示例和验收测试。
- 建立贡献指南、架构决策记录、Feature SDK 文档和安全规范。
- 通过社区模板、定制开发和托管支持形成长期项目价值。

### 阶段验收

- 开发者可以按照公开协议创建并安装一个独立 Feature。
- 扩展可以独立启停，扩展失败不影响核心服务启动。
- 用户可以从模板或 AI 对话开始构建业务系统，并在同一个组织权限体系下运行。
- 核心、Feature 和扩展具备清晰的版本、迁移、备份和回滚路径。
- 项目依然可以在一台 Windows、macOS 或 Linux 机器上通过源码和脚本运行。
- 社区开发者能够理解项目边界，不需要阅读全部核心代码就能开发扩展。

## 五、当前执行顺序

1. 补齐首版核心的认证、组织和权限负向测试。
2. 增加成员生命周期、审计日志和系统权限管理界面。
3. 固化 Feature Manifest 和声明式数据模型。
4. 实现动态列表、表单、详情、权限和基础数据操作。
5. 把 AI 对话接入受控 Feature 工具，支持方案预览和确认发布。
6. 增加 Feature 版本、停用、回滚和备份恢复。
7. 建立 AI 开发上下文、任务模板和自动验收命令。
8. 再评估复杂代码扩展是否需要独立本地进程。
9. 最后建设 SDK、模板生态和稳定版本体系。

## 六、最终产品边界

Bixi Seed 的目标不是提供最多的企业功能，而是提供一套足够安全、足够简单、边界清晰且可以继续生长的应用基础。

组织权限保证业务边界，Django 保证核心稳定，Vue 提供统一交互，Feature 引擎承载普通业务，AI 负责降低创建和修改业务功能的门槛。复杂能力只有在真实需求出现后才进入扩展层。

参考资料中的其他项目主要用于借鉴阶段划分、验收标准、AI 风险控制、本地数据保护和统一模型设计；它们的项目定位、技术栈和部署指令不直接作为 Bixi Seed 的实施要求。
